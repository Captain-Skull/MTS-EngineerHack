# 0008. Трейсинг OpenTelemetry → Tempo

**Статус:** принято

## Контекст

Метрики показывают, что что-то не так, логи — что произошло в отдельном компоненте. Чтобы увидеть путь одного запроса через Envoy и версию приложения и время каждого шага, нужен третий сигнал — трейсы.

## Решение

Envoy и nginx (сборка образа с модулем `otel`) отправляют спаны по OTLP в **OpenTelemetry Collector**. Он добавляет атрибуты Kubernetes и пересылает спаны в **Tempo**. Metrics-generator Tempo строит граф сервисов и span-метрики и пишет их в Prometheus. `trace_id` попадает в access-логи, и Grafana связывает «лог ↔ трейс».

## Альтернативы

- **Jaeger** — зрелый, но отдельный UI и хранилище (Elasticsearch/Cassandra для production).
- **Отправка напрямую в Tempo без Collector** — меньше компонентов, но нет обогащения метаданными Kubernetes и единой точки для семплирования и смены бэкенда.

## Последствия

- Три сигнала наблюдаемости связаны в одной Grafana.
- Семплирование 100% подходит для стенда; в production долю трейсов снижают (`samplingRate`) или используют tail sampling в Collector.
- Приложение не изменено: трейсинг добавлен на уровне прокси и модуля веб-сервера.
